# dsh-memory Phase 1 架构第三方评审报告

## 1. 总体评价

**结论：有条件通过。**

你的方案并非“方向错误”，相反，它抓住了两个已被外部实践反复证明的重要点：  
1) **记忆必须是可审计、可编辑、可清理的**，不能完全黑盒；  
2) **常驻上下文必须严格受预算约束**，否则记忆系统会反过来伤害主工作流。  

但它当前的 **Phase 1 边界仍偏大，且若把“Claude Code 式自动抽取”与“AI_Prompt 式确认流”同时放进早期版本，会产生明确的产品张力**：一边追求“无感自动化”，一边又要求“下次会话人工确认归档”，这两条机制在 UX 和心智模型上并不天然一致。外部案例表明，**自动记忆最常见的问题不是“记不住”，而是“记错、记旧、记得太多、打断主任务”**；而纯手工/强确认流最常见的问题则是**“用户和模型都懒得维护，最后形同虚设”**。所以它不是不能做，而是 **Phase 1 必须进一步收缩，只保留最能证明价值、最少引入反作用的那一组能力**。

如果你把 Phase 1 定义为：**工作区级、Git 可共享、Markdown 可审计、索引常驻受预算约束、检索默认走全文/grep/BM25、写入以显式或半显式确认为主**，那这条路线是成立的。  
如果你坚持在 Phase 1 同时上：**turn-end 自动抽取 + 强确认流 + 复杂状态文件 + 多层检索增强**，我倾向于认为风险过高，且会把最宝贵的早期反馈信号污染掉。

## 2. 方案合理性评估

### 2.1 架构是否自洽：Claude Code 骨架 + AI_Prompt 确认流，是不是一条成立的“第三条路”？

**结论：在“读路径”上自洽，在“写路径”上存在内生张力。**

#### 自洽的部分
1. **索引常驻 + 细节外置** 是合理的  
   这点与 Claude Code 的方向一致。外部公开反馈已经证明：把全部记忆正文持续注入上下文会迅速制造 token/缓存成本与噪声问题。  
   - Claude Code 社区对 `MEMORY.md` 预算问题的公开反馈非常具体：在 issue **#83114** 中，重度用户报告单项目已有 **1200+ memory fact files（约 26MB）**，而 `MEMORY.md` 长期卡在自动加载预算附近，导致“每次记忆写入都要在工作中途手工修索引”，用户原话是：  
     > “MEMORY.md went 55 bytes over cap — trimming my own line.”  
     这说明“常驻只放索引，正文按需读”不是品味选择，而是**工程必要性**。  
   - 相关成本问题也在 issue **#42272** 里被量化：用户报告系统前置内容（`CLAUDE.md` + `MEMORY.md` + plugin/skill 描述）合计约 **35–40K tokens**，简单问两三个问题就消耗大量 usage。  

2. **知识/约束分离** 是正确的  
   这点不仅在你的文档中成立，在外部产品实践中也成立。Cline 官方 Memory Bank 文档明确把 Memory Bank 定位为项目知识与状态文档，而规则/自定义指令仍归 rules/custom instructions 管。  
   - Cline 官方文档：Memory Bank 用于 `projectbrief.md / productContext.md / activeContext.md / systemPatterns.md / techContext.md / progress.md` 六类项目知识，而它的 custom instructions 则定义“必须先读全部 memory bank files”这类行为约束。  
   这说明“**行为约束**”和“**项目知识**”分开，是社区已形成的稳定结构，不是你的独创假设。

3. **工作区级持久化** 在 DSH 生态里有真实位置  
   DSH 现有公开插件中，至少已有几条明显不同路线：  
   - `@max-null/dsh-memory`：**明文 + BM25 + no embeddings**，并明确区分 `global` 与 `project` 两层；其 README 直接写明  
     > “project 命名空间的记忆落在项目文件夹内……可 git 分享。”  
   - `@meomeo-dev/dsh-memory`：**JSONL truth source + Markdown projection + semantic facts**。  
   - `dsh-memory-gate`：不做“存储本体”，而做 **retrieved ≠ injected** 的使用闸门与审计。  
   - `dsh-mnemon`：走 **three-tier memory control plane**，更像统一记忆控制层。  
   这说明“工作区记忆”并不是伪需求；但它不是唯一答案，而是生态里的一个明确分支。

#### 存在张力的部分
1. **“turn-end 自动抽取”与“经验确认流”在产品心智上冲突**
   - Claude Code 的自动记忆价值在于：**不中断，不依赖用户/模型自觉**。  
   - AI_Prompt 式确认流的价值在于：**人类最终把关，降低误记忆/垃圾记忆进入长期层**。  
   这两者叠加后，用户会很快遇到一个问题：  
   **到底“已记住”是什么意思？**  
   - 如果自动抽取写进了临时区，但没确认，它算不算可被检索和注入？  
   - 如果它可被注入，那确认流就失去质量闸门意义。  
   - 如果它不可被注入，那自动抽取对主体验的价值会显著下降。  

2. **“工作区 Git 共享”与“个人偏好/用户信息”天然冲突**
   Claude Code 用户已经在公开 issue 中提出相反方向的诉求：  
   - issue **#83831** 请求增加 **user-level (cross-project) scope for auto-memory**，理由是很多 runbook、VPN、AWS SSO 登录等知识不是 repo-specific，而是 user/machine-wide。  
   - issue **#74740** 则反映了另一种痛点：多个同源项目之间希望共享 memory。  
   这两条反馈共同证明：**单一 scope 不够**。  
   你的方案如果在 `.dsh/memory/` 里同时放 project facts 和 user facts，会很快陷入污染、泄露、不可提交或不敢提交的问题。  
   所以 **工作区级 memory 可以成立，但 Phase 1 必须非常严格地限定其内容类型**，最好只允许项目共识，不碰个人偏好与环境私密信息。

3. **200 行硬边界“照抄”Claude Code，但你的系统目标和 Claude Code 不同**
   Claude Code 的 memory 是**用户级、本地级、官方内建**，你的目标是**工作区级、可提交、团队可见**。  
   因此同样的 200 行预算可以作为“常驻注入预算”，但不能直接等同于“整个系统的核心边界”。  
   否则很容易出现：  
   - 索引够了，但团队知识已经碎到不可维护；  
   - 或索引没超，但 recall 体验已经明显退化。

### 2.2 相比“完全照搬 Claude Code”与“完全照搬 Cline Memory Bank”，融合方案的净优势

#### 相比完全照搬 Claude Code 的净优势
1. **可共享、可审计、可 Git 历史追踪**  
   Claude Code 的 auto-memory 默认在 `~/.claude/projects/<project>/memory/`，对协作和换机迁移不友好。  
   外部 issue 证明这个缺点是真实的，不是理论上的：  
   - **#74740**：用户明确希望相似项目之间共享 memory。  
   - **#83831**：用户希望 user-level cross-project scope。  
   这些都说明现有 per-project local-only scope 不足。  
   你的工作区目录方案在“项目记忆应随仓库流动”这件事上，**比 Claude Code 更契合团队协作**。

2. **确认流能降低错误固化**
   Claude Code 社区已经出现多类“记忆误导”问题：  
   - **#83415**：模型在可读到真实文件时，仍基于 memory index 一行摘要编造了错误协议说明。  
   - **#74136**：长会话/压缩后 fabricated user instruction、fabricated verification results。  
   - **#86420**：用户直接抱怨“Claude ignores project context and memories, requires constant redirection”。  
   所以“自动写入后直接生效”并不天然安全。  
   你的确认流至少在理论上能减少“错误长期知识被直接提权”的概率。

3. **更符合 DSH 插件生态的可组合性**
   DSH 生态已有多种 memory 插件路线：明文/BM25、JSONL 事实源、SQLite gate、三层控制平面。  
   你若坚持 Markdown/source-of-truth + 索引 + 工具式 recall/update，将比“强绑定某个内建 memory runtime”更容易与 DSH 现有能力拼接。

#### 相比完全照搬 Cline Memory Bank 的净优势
1. **不完全依赖模型自律**
   Cline 官方方案明确要求：  
   > “I MUST read ALL memory bank files at the start of EVERY task - this is not optional.”  
   这是一种方法论，而不是系统级保障。  
   外部经验反复表明：**“MUST” 写在提示词里，不等于模型长期稳定遵守。**  
   Claude Code 用户甚至在别的问题里明确说 CLAUDE.md、memory.md、软提醒都“不 reliably obeyed”（见 **#76524** 中用户对“brevity principles、memory.md files、soft hook reminders all fail”的反馈）。  
   你的自动注入思路在这里明显优于纯文档纪律。

2. **上下文成本更可控**
   Cline Memory Bank 文档本质上鼓励“任务开始先读全部”，这对小项目可以，对长期项目会持续放大 token 成本。  
   社区已经在类似体系里做 lazy-loading 降本：你的文档引用的 substrate PR 降本约 70% 虽不是 DSH 官方，但它至少说明“eager 全量读入”在真实社区是被反向优化的。  
   因此你的索引化设计有明确成本优势。

---

### 2.3 融合方案的额外风险

1. **双重复杂度风险：自动抽取复杂 + 人工确认复杂**
   你不是在 A 和 B 里二选一，而是在早期版本里同时背两套失败模式。  
   - 自动抽取失败模式：误记、漏记、打断、索引膨胀、陈旧化  
   - 确认流失败模式：用户忽略、积压、永远不归档、状态含糊  
   对 Phase 1 来说，这个组合过重。

2. **Git 共享与并发写冲突风险**
   Claude Code 已有公开 issue 暴露记忆文件并发写风险：  
   - **#85597**：两个并发 session 共享 `~/.claude`，`Write` 工具会 **silent overwrite** 另一个 session 的 memory/rules 文件，无锁、无合并、last writer wins。  
   虽然你的存储位置不同，但如果 Phase 1 支持多个 agent / 多窗口 / 团队同时改 `.dsh/memory/`，同类问题几乎必然出现。  
   **文件格式透明 ≠ 并发安全。**

3. **“自动写入可回溯”不等于“用户愿意维护”**
   很多团队口头上喜欢“可 Git、可审计”，但真正到每次 commit 都出现 memory diff 时，可能迅速变成噪音。  
   当前没有足够外部证据证明“工作区 memory 文件进入 Git 提交流”会被广泛欢迎；相反，现有公开插件往往会明确区分 global/project 或把 truth source 放在较独立位置，正是因为这个 tension 真实存在。

## 3. 关键假设验证

---

### 假设1：Turn-end 自动抽取能可靠地捕获“值得记住”的信息

**结论：证据不足，且从现有社区反馈看“不可靠”更接近事实。**

#### 支持它的证据
- Claude Code 官方产品路线本身就是强支持信号：它确实在做自动 memory。
- 用户无需手动维护，这一点在产品 ergonomics 上有天然优势。

#### 反证/削弱证据
1. **Claude Code 用户明确报告 memory 被忽略、误用、答非所问**
   - issue **#86420**：  
     > “Claude ignores project context and memories, requires constant redirection”  
     这说明即便 memory 存在，也不代表它会稳定发挥正作用。
2. **memory index 一行摘要会诱发“拿摘要当真相”的误答**
   - issue **#83415**：模型没有读真实文档，而是从 persistent memory index 的一行总结中编造出“项目规范”。  
     这说明自动抽取即使捕获了“某些信息”，也**不等于它以正确粒度被后续消费**。
3. **长会话/压缩后会出现 fabricated user instruction 与 fabricated verification**
   - issue **#74136**：用户报告压缩/长期会话后，模型 fabricated commit、fabricated verification results，甚至 fabricated user instruction。  
   这并不直接证明 auto-memory 写错，但明确说明：**把会话后处理/自动压缩/自动提炼交给模型，本身不是高可靠过程。**
4. **用户推动“bridge/compaction”类辅助流程，恰恰说明自动捕获并不够**
   - PR/issue **#27140** 提出 `/bridge`：structured context consolidation at session boundaries。  
   这类社区自发补丁的存在，本身说明原生自动记忆并没有让“会话结束后的知识沉淀”问题消失。

#### 判断
- 自动抽取**可以**作为“漏斗入口”，  
- 但把它视为“可靠地抓住值得记住的信息”的前提，**过于乐观**。  
- 更准确的定位应是：**自动抽取是召回候选的生成器，不是真理过滤器。**

---

### 假设2：200 行硬边界是必要且足够的

**结论：必要性大体成立；“足够”不成立。**

#### 必要性的证据
1. **常驻上下文必须控预算**
   - issue **#42272**：用户报告仅 system prompt 相关前置信息就达到 **35–40K tokens**，直接推高使用成本。
   - issue **#19105**（虽为用户提案，但反映了真实痛点）：用户认为 baseline “hi” 的会话启动就可能消耗 **~53k tokens**，并请求 lazy-loading 架构。
2. **MEMORY.md 高水位会直接打断工作**
   - issue **#83114**：`MEMORY.md` 长期顶在约 **17KB auto-load budget**，新记忆写入逼得工作中途反复修 index。  
   所以“没有硬预算”基本不可行。

#### “足够性”被削弱的证据
1. **重度用户已证明 200 行/17KB 不是长期足够**
   - issue **#83114**：单项目 1200+ memory fact files，说明索引预算很快成为长期瓶颈。  
   用户自己提出的需求也不是取消上限，而是：
   - 原生生命周期管理
   - hysteresis/high-water-mark
   - 把 compaction 移出工作会话
2. **记忆量增长不是线性的知识价值增长**
   200 行不是“知识上限”，只是“常驻索引上限”。  
   真正需要的是：
   - 常驻索引预算
   - 二级/三级按需读取
   - 生命周期/归档/命中统计  
   只靠“200 行”这个数字本身不能保证 recall 质量。

#### 判断
- **必要**：是。  
- **足够**：否。  
- 正确表述应为：  
  **“Phase 1 需要一个硬预算上限，但它只是常驻注入上限，不是整体记忆系统充分条件。”**

---

### 假设3：工作区 `.dsh/memory/` 可提交 Git 是用户真实需要的

**结论：有真实需求，但不是普适需求；必须做内容边界与 scope 分层。**

#### 支持证据
1. **DSH 生态已有明确把 project memory 放进仓库的公开插件**
   - `@max-null/dsh-memory` README 直接声明：
     - `global` 放 `$DSH_HOME/storages/memory.json`
     - `project` 放 `<cwd>/.dsh/storages/memory_project.json`
     - project memory “可 git 分享”
   这说明“仓库随行的项目记忆”不是你一家的想象。
2. **Cline 官方 Memory Bank 本质也是 repo-level 文档方案**
   - 官方建议把 rules / memory-bank 放在项目里，便于团队共享。
3. **Claude Code 用户确实反复遇到 scope 不合适的问题**
   - **#74740**：希望相似项目共享 memory。  
   - **#83831**：希望 user-level cross-project memory。  
   反过来看，这说明“仅本地私有 per-project”并不能覆盖所有需求，因此 repo-level/project-level scope 具备存在价值。

#### 反证/风险证据
1. **repo-level 不等于所有内容都适合提交**
   - 如果把 `user` 类记忆、机器环境、认证/偏好、runbook 混入 `.dsh/memory/`，会直接触发隐私与噪音问题。
2. **并发与冲突是实打实的工程问题**
   - **#85597** 显示 memory/rules 文件的 whole-file write 在并发 session 下可能 silent overwrite。  
   一旦 memory 被 Git 管理，多人/多 session 同时改动会更常见，而不是更少。
3. **提交噪音会伤害 adoption**
   没有公开大样本能证明“团队普遍乐于把记忆文件纳入主线版本控制”。  
   更现实的情况是：只有**项目共识类、稳定类**内容适合入库；**会话态、候选态、用户态**内容不适合。

#### 判断
- “工作区记忆可 Git”是**真实但有边界的需求**。  
- Phase 1 不应把它描述成默认对所有记忆都成立。  
- 正确做法应是：
  - **project/shared**：可入库  
  - **user/private**：默认不入库  
  - **candidate/staging**：默认不入库或单独忽略

---

### 假设4：grep / 全文检索足以满足大多数检索需求

**结论：对 Phase 1 来说基本成立；对长期上限来说不成立。**

#### 支持证据
1. **DSH 公开竞品已明确以 BM25 / plaintext / no embeddings 为卖点**
   - `@max-null/dsh-memory` 描述：  
     > “Cross-session plaintext memory plugin … deterministic BM25 recall, human-owned, no embeddings”
   这说明在 DSH 生态里，**“不用 embeddings 也能做出有吸引力的 memory 产品”** 已被公开验证。
2. **你的直接竞品中，至少一类强调“retrieved ≠ injected”，不是强调 RAG**
   - `dsh-memory-gate` 强调本地 SQLite + FTS5 + bounded + no extra model call，卖点在**使用决策闸门与审计**，而非向量召回。
3. **Cline 官方方案也完全不是 RAG-first**
   - 本质是文档法，而不是检索系统。

#### 反证/边界证据
1. **字面匹配错位是公开已知问题**
   你的文档中引用“port conflicts vs docker-compose port mapping”这类例子，本质上就是全文/grep 的已知弱点。  
   虽然我没拿到 Claude 官方文档原文验证 Boris Cherny 的“grep > RAG”那句，但从公开 issue 看，**并没有足够官方公开证据证明 lexical search 足以覆盖长期复杂记忆检索**。
2. **更重型 DSH 竞品显然已经往语义/控制平面走**
   - `@meomeo-dev/dsh-memory`：semantic facts + multi-node recall  
   - `dsh-mnemon`：three-tier memory control plane, searchable project documents, pluggable long-term memory, smart routing  
   这说明生态里已经有人认为纯 lexical 不够，至少在更复杂场景下不够。
3. **Claude Code 社区用户已在实践中感到“索引/摘要/关键词”不足**
   - **#83415** 的问题之一就是摘要太短，模型从一行总结错误重建了实际协议。  
   虽然这不是“grep 失败”的直接例子，但说明**低粒度摘要 + 非验证式消费**会出严重问题。

#### 判断
- 对 **Phase 1 MVP**：  
  **是，grep/BM25/全文足够。**  
- 对 **中长期愿景**：  
  **不足以作为唯一答案。**  
- 因为你的差异化不是“最强语义检索”，而是“工作区级、可审计、可共享、低复杂度的长期记忆”。

## 4. 竞争定位与差异化建议

### 4.1 DSH 生态中的竞争格局

基于公开 npm/仓库元数据，当前 DSH 记忆生态至少有这几条路线：

1. **明文/BM25/人类所有权路线**
   - `@max-null/dsh-memory`
   - 核心卖点：plaintext、BM25、human-owned、no embeddings、global/project 双层

2. **语义事实/JSONL 真相源路线**
   - `@meomeo-dev/dsh-memory`
   - 核心卖点：semantic facts、JSONL truth-source、Markdown projection、warm multi-node recall team

3. **使用闸门/审计路线**
   - `dsh-memory-gate`
   - 核心卖点：retrieved ≠ injected、verify/use/ignore 决策、SQLite + FTS5、本地 bounded、无额外模型调用

4. **统一控制平面/多层记忆路线**
   - `dsh-mnemon`
   - 核心卖点：three-tier memory control plane、searchable project documents、pluggable long-term memory、smart routing、WebUI

从这个格局看，**你的方案如果继续“什么都做一点”会非常危险**。  
因为别人已经分别占了：
- 检索算法
- 语义记忆
- 控制平面
- gate/audit
- UI/多节点

### 4.2 你的真正独特壁垒是什么？

**最有机会形成壁垒的，不是“又一个 memory plugin”，而是：**

> **“工作区级、可 Git 协作、可读可审计的项目知识记忆层，并且用显式确认/归档流程保证长期质量。”**

换句话说，你的 strongest differentiator 不是：
- 检索最强
- 自动化最强
- 语义最强
- UI 最强

而是这四个组合：
1. **工作区共享**  
2. **Markdown/source-of-truth 可审计**  
3. **索引常驻受预算约束**  
4. **人类确认流防止长期污染**

这是一条比“做另一个向量记忆系统”更清晰的位置。

### 4.3 是否存在“面面俱到却无突出亮点”的风险？

**结论：存在，而且已经出现苗头。**

风险点主要在：
- 想借 Claude Code 学自动抽取
- 想借 AI_Prompt 学确认流
- 想借 meow / mnemon 学检索增强与反思
- 想保留跨工作区、可逆归档、状态文件、阶段演进……

这会把产品叙事稀释成：  
**“我们也有一点这个，也有一点那个。”**

### 4.4 应该砍掉哪些特性，专注哪个方向？

#### 建议专注方向
**专注为：`repo-scoped auditable memory for project consensus`**

也就是：
- 项目共识
- 架构决策
- 排障经验
- 稳定工作约定

而不是：
- 通用个人偏好库
- 自动成长型 agent memory OS
- 跨工作区全域联想
- 高级语义路由平台

#### 建议推迟/砍掉
1. **Phase 1 不做 turn-end 自动抽取落正式库**
2. **Phase 1 不做跨工作区 recall**
3. **Phase 1 不做复杂 fuzzy/语义检索增强**
4. **Phase 1 不做太重的状态机/多文件状态体系**
5. **Phase 1 不碰 user/profile 类长期记忆**

## 5. 工程陷阱预警与缓解措施

### Top 1：索引预算与常驻注入膨胀，最终反噬主工作流

#### 证据
- Claude Code issue **#83114**：`MEMORY.md` 长期顶在预算，工作中途不断修索引。
- Claude Code issue **#42272**：system prompt 开销 35–40K tokens，简单任务 usage 异常高。
- Claude Code issue **#19105**：用户明确要求 lazy-loading architecture，认为可节省 60–70% baseline 开销。

#### 失败模式
- 记忆系统本想“帮助上下文”，结果先把上下文税抬高；
- 越用越卡，越用越贵；
- 用户开始把 memory 视为负担而非增益。

#### 缓解
1. **常驻只注入 index + 最小 state 摘要**
2. **给 index 设双阈值，不只单阈值**
   - 高水位触发整理
   - 整理后降到低水位，不做 55-byte 式微修
3. **整理/归档必须脱离主任务路径**
   - 不允许在工作回合中途做 compaction
4. **必须有 recall hit telemetry**
   - 否则清理只能拍脑袋

---

### Top 2：自动写入/并发写导致长期知识污染或静默丢失

#### 证据
- Claude Code issue **#85597**：并发 session 写 memory/rules 文件，whole-file `Write` silent overwrite，last writer wins。
- Claude Code issue **#86525**：同一 session 内 read key / write key 错位，造成 memory split。
- Claude Code issue **#80615**：memory settings 关闭了仍然继续写 memory 文件，说明 memory gating/状态一致性本身就容易出错。

#### 失败模式
- 两个 agent 或两个窗口改同一 memory 文件，内容静默丢失；
- 自动抽取把错误内容推进长期层；
- 用户以为有审计，其实丢失是静默发生的。

#### 缓解
1. **Phase 1 严禁 whole-file blind write**
   - 必须增量 append 或有 optimistic locking
2. **memory update 工具必须带 freshness check**
3. **候选态与正式态分文件或分区**
4. **多会话写入先不支持并发合并，明确单 writer 约束**
5. **对 Git/shared 层引入最简冲突标记或 rewrite check**

---

### Top 3：“经验确认流”被用户忽略，最终变成积灰待办

#### 外部旁证
虽然公开 issue 很少直接讨论“确认流”，但大量外部实践已经说明：  
- 纯文档维护方法会衰减（Cline Memory Bank 的根本短板就在这里）  
- 软提醒、CLAUDE.md、memory.md 并不可靠（见 **#76524** 用户明确说 rules / memory files / reminders all fail）  
- 社区不断造 `/bridge`、compact、review、custodian 这类额外机制，本质上就是因为“靠人想起来做”不行

#### 失败模式
- 候选记忆越积越多，从不确认；
- 用户把提醒当噪音点掉；
- 最后系统同时失去自动化优势和高质量优势。

#### 缓解
1. **不要做“下次会话统一提醒一长串”**
   - 这是最容易被跳过的形态
2. **改成“任务结束后 1~2 条极短候选，内联确认/忽略”**
   - 在上下文还热的时候处理
3. **候选记忆必须极少**
   - 每次最多 1~3 条
4. **优先确认高价值类型**
   - decision / troubleshooting
   - 不要让 pattern/user 先淹没流量
5. **如果 3 次连续未确认，就自动降级为仅日志，不再打扰**

## 6. MVP 精简建议

## Phase 1 必做清单

### 6.1 存储与边界
- 工作区目录：`.dsh/memory/`
- **只存项目共识类记忆**
  - `decisions`
  - `patterns`
  - `troubleshooting`
- **不存 user/personal/private** 到工作区正式库
- Markdown 为可读真相源，必要时可派生 index

### 6.2 注入与预算
- 常驻只注入：
  - `index.md`
  - 极简 `state.md` 摘要（如果你坚持保留 state）
- 必须有硬预算：
  - 行数/字节双限都可以
  - 但把它定义为**常驻注入预算**，不是系统充分条件
- 超限行为：
  - 明确 warning
  - 不要静默截断
  - 不要在主任务回合中强迫即时整理

### 6.3 检索
- `memory_recall`
  - 先 index
  - 再全文/BM25/grep
- 不上向量检索
- 不上复杂语义路由
- 不上跨工作区 recall

### 6.4 写入
- **只做显式写入或半显式写入**
  - 用户说“记住这个”
  - 或任务结束时给出 1 条候选供立即确认
- 正式库写入必须带：
  - 类型约束
  - 去重/覆盖基本规则
  - freshness / append 安全约束

### 6.5 质量守则
- 在系统提示或工具说明里明确：
  > 记忆只是提示，涉及规则/协议/代码事实时，优先回源验证真实文件。

这点很重要，外部 issue **#83415** 已证明：如果不写死这个原则，模型会把 memory index 一行摘要当权威。

## Phase 1 明确推迟 / 不做清单

### 推迟到 Phase 2 以后
- turn-end 自动抽取直接写正式记忆
- 经验暂存跨会话确认的大队列机制
- cross-workspace recall
- fuzzy token 重叠 / bigram / keyword 自动提取增强
- 会话级已见去重
- reflect 式自动反思
- 自动 compact / dream / custodian
- user/global 层与 project 层混合调度
- UI 面板
- 复杂状态机

### 建议完全不做，至少不要作为主线
- 在 Phase 1 引入向量检索 / 图谱 / RAG
- 试图成为通用 memory operating system
- 同时解决“项目记忆、用户记忆、跨项目 runbook、跨工具共享”四类问题
- 把自动抽取结果默认当成正式长期知识

## 最终裁决

**裁决：有条件通过。**

**通过条件只有三条：**
1. **Phase 1 缩回到“工作区项目共识记忆”**，不要试图同时做自动智能记忆平台。  
2. **把“常驻预算控制”当作第一约束，而不是后补优化。**  
3. **把“自动抽取”降级为候选生成，而不是正式记忆真理源。**

如果按这个方向收缩，你的方案会有清晰定位：  
**不是另一个花哨 memory engine，而是 DSH 里最可审计、最适合团队项目共识沉淀的工作区记忆层。**

如果不收缩，而是坚持在 Phase 1 同时上自动抽取、确认流、复杂状态、共享/跨域/增强检索，那么我对首版成功率持明显保留态度，原因不是概念不对，而是**你会在最早期同时承担四类不同产品的复杂度。**
